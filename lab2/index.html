Лабораторная работа 2. Потоки. Процессы. Асинхронность

Студент: Макаров Егор

Цель работы: понять отличия между потоками и процессами и разобраться, что такое асинхронность в Python; на практике сравнить threading, multiprocessing и asyncio на CPU-bound и I/O-bound задачах.

Теоретическая основа

Подход Параллелизм Где выигрывает Причина
threading псевдо-параллелизм (1 ядро) I/O-bound Из-за GIL одновременно Python-байткод исполняет только один поток. На время ожидания I/O GIL освобождается, поэтому потоки полезны при сетевых/дисковых операциях, но не на вычислениях.
multiprocessing настоящий параллелизм (N ядер) CPU-bound Каждый процесс — свой интерпретатор и свой GIL. Вычисления идут реально параллельно, но создание процессов и обмен данными между ними дороже.
asyncio конкурентность (1 поток) I/O-bound Кооперативная многозадачность через цикл событий. Эффективна при большом числе ожиданий I/O, но не ускоряет вычисления.

GIL (Global Interpreter Lock) — глобальная блокировка интерпретатора CPython, не дающая нескольким потокам одновременно исполнять байткод. Именно поэтому threading не ускоряет CPU-bound задачи, а для них нужен multiprocessing.

Задача 1. Сумма чисел от 1 до N

Каждая программа содержит функцию calculate_sum(start, end), которая в цикле суммирует числа на отрезке (а не по формуле Гаусса — чтобы создать реальную CPU-bound нагрузку). Отрезок [1, N] делится на 8 равных подзадач функцией split_ranges, подзадачи выполняются параллельно, затем частичные суммы складываются.

По заданию N = 10¹³. Полный перебор 10¹³ чисел в чистом Python занял бы десятки часов, поэтому замеры проведены на 10⁸ и 10⁹ (значение задаётся аргументом). Соотношение времён между подходами от размера N не зависит.

Результаты (8 подзадач, 10-ядерный CPU, корректная сумма во всех случаях):

N threading multiprocessing async
10⁸ 2.44 c 0.51 c 2.30 c
10⁹ 23.93 c 3.85 c 24.39 c

Вывод по задаче 1: на CPU-bound вычислениях выигрывает только multiprocessing (ускорение ≈ ×6 на 10 ядрах). threading и asyncio работают со скоростью однопоточного решения — потоки упираются в GIL, а корутины в принципе выполняются в одном потоке и не отдают управление во время счёта.

Задача 2. Параллельный парсинг веб-страниц

Каждая программа содержит функцию parse_and_save(url): загружает HTML-страницу, извлекает её <title> (через BeautifulSoup), сохраняет в БД и печатает результат. Список из 10 URL делится на равные части (split_into_chunks, по числу воркеров WORKERS = 3 → части по 4, 3, 3), и каждый воркер (поток / процесс / корутина) обрабатывает свою часть в цикле, вызывая parse_and_save. Загрузка: requests для threading/multiprocessing, aiohttp для async.

Сохранение в БД. Данные пишутся в ту же базу, что и в ЛР1 (hackathon_fastapi), в отдельную таблицу parsed_pages (id, url, title, approach, parsed_at). Каждое сохранение открывает собственное короткоживущее соединение (psycopg2) — это безопасно и для потоков, и для процессов.

Результаты (10 страниц, 3 воркера; для контраста приведён последовательный замер):

Подход Замер 1 Замер 2
sequential (база) 8.77 c —
threading 3.13 c 4.29 c
multiprocessing 4.35 c 4.32 c
async 5.89 c 4.34 c

Вывод по задаче 2: все три параллельных подхода примерно вдвое быстрее последовательного — парсинг I/O-bound, и пока один запрос ждёт ответ сети, выполняются другие. Ускорение ограничено числом воркеров (3 части вместо 10 одновременных запросов). Разница между threading / multiprocessing / async невелика и во многом определяется «шумом» сети (поэтому приведено несколько замеров). При этом:

  • async (aiohttp) — самый лёгкий по ресурсам: тысячи запросов в одном потоке без накладных расходов на потоки/процессы. Лучший выбор для массового I/O.
  • threading — почти так же быстр и проще в коде; отличный вариант для умеренного числа запросов.
  • multiprocessing — тоже ускоряет, но избыточен для I/O: создание процессов дороже, а на сетевых ожиданиях это преимущество не нужно.

Итоговые выводы

CPU-bound (Задача 1) I/O-bound (Задача 2)
threading ❌ нет ускорения (GIL) ✅ ускоряет
multiprocessing ✅ лучший (реальный параллелизм) ✅ ускоряет, но избыточен
asyncio ❌ нет ускорения ✅ лучший (минимум накладных расходов)

Главный практический вывод: выбор подхода зависит от типа нагрузки. Для вычислений (CPU-bound) нужен multiprocessing, обходящий GIL; для операций ввода-вывода (CPU-bound отдыхает, ждём сеть/диск) — asyncio или threading, которые дают конкурентность без затрат на отдельные процессы.
